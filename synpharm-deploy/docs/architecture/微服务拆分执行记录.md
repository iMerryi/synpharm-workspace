# 微服务拆分执行记录与后续切分方案

> 版本 v1.0 · 2026-11-04 · 状态：**第一步已完成并实测**（platform / asset 已独立），
> 设计域的 7 块切分方案已定、待执行。

---

## 0. 一句话结论

`synpharm-core` 现在装的是**设计域一个限界上下文**，不是"三个服务硬塞在一起"。
但设计域内部有 7 个可切的子域，其中 2 个（platform / asset）**与设计域双向零 import**，
已于 2026-11-04 摘出。剩下 7 块要切，必须先解决 `candidate_molecule` 的多写入方问题。

---

## 1. 这一步做了什么

### 1.1 从 core 摘出两个服务

| 新服务 | 端口 | 独占表 | 代码量 | 依据 |
|---|---|---|---|---|
| `synpharm-platform` | 8084 | `design_tool`（`synpharm_platform`） | 24 类 | 与设计域双向零 import；变更节奏独立（引擎加算子就要动它）；定时探测不该占设计域连接 |
| `synpharm-asset` | 8085 | `file_asset`（`synpharm_asset`） | 6 类 | 同为零 import；唯一需要 200MB multipart 的服务，合并期把设计域的限额一起放开了 |

### 1.2 路径收敛为语义前缀

| 旧路径 | 新路径 | 为什么要改 |
|---|---|---|
| `/api/design/tools/**` | `/api/platform/tools/**` | 一个前缀对两个服务，只能靠"platform 路由必须排在 core 之前"维持正确 |
| `/api/design/capabilities` | `/api/platform/capabilities` | 同上 |
| `/api/system/algorithm-health` | `/api/platform/algorithm-health` | `/api/system` 是单体时代的通用前缀，多服务下无意义 |

`/api/system/**` 现在是 **404**（网关无此路由），这是有意的破坏性变更，已在前端与文档同步。

### 1.3 新增 `synpharm-api` 模块

服务间契约（Feign 接口 + 跨服务 DTO）。当前只有一个契约：

```java
@FeignClient(name = ServiceNames.PLATFORM, path = "/internal/tools")
public interface PlatformToolApi {
    @GetMapping("/registry") Result<List<ToolRegistryItem>> registryEnvelope();
    default List<ToolRegistryItem> registry() { /* 把三种失败都翻成 503 */ }
}
```

配套自动装配 `SynpharmApiAutoConfiguration` 注册 `InternalTokenFeignInterceptor`：
**所有 Feign 调用自动带上 `X-Internal-Token` 与 `X-User-Id`**。这一步不能省 ——
让每个调用方自己记得加头，漏一个的表现是"某个功能突然 500"，排查要从业务看到过滤器。

## 2. 拆解中踩到的两个隐式耦合（本次最重要的产出）

这两个都不是"看 import 就能发现"的，靠静态扫描会漏，必须跑起来才知道。

### 2.1 Bean 依赖：设计域的 `ChemistryClient` 注入的 `WebClient` 定义在 platform 包里

```
design/infrastructure/client/ChemistryClient.java   →  private final WebClient fastApiWebClient;
platform/support/WebClientConfig.java               →  @Bean fastApiWebClient()
```

两个包之间**没有任何 import**，耦合藏在 Spring 的按类型注入里。把 platform 摘走后，
core 会以 `no qualifying bean of type WebClient` 启动失败。

**处置**：给设计域写一份自己的 `FastApiWebClientConfig`，**不是**塞进共享库。
拆成两个进程之后它们本来就是两个客户端，各自的 base-url、超时、API Key 都可能不同；
共享一个 Bean 只会把两个服务的配置绑死。

### 2.2 领域依赖：设计域的命令面板直接 import 了 platform 的应用服务

```
design/application/impl/WorkspaceAppServiceImpl.java
  import com.synpharm.platform.application.ToolAppService;
  import com.synpharm.platform.api.dto.ToolRegistryItem;
```

`/api/design/commands` 用「项目状态（设计域）」+「工具注册表（平台域）」拼出命令列表。
这是**真实的跨域读**，必须改成 Feign。

**处置**：`ToolRegistryItem` 移到 `synpharm-api`（两个服务共用一份定义），
platform 加 `/internal/tools/registry`，设计域改注入 `PlatformToolApi`。

> **教训**：拆分前做耦合分析，不能只 grep import。
> 还要查 ① `@Bean` 返回类型被谁注入 ② `@ConfigurationProperties` 前缀被谁读
> ③ 静态单例 / ThreadLocal。本次的扫描脚本还犯了一个错误：在 `design/` 目录下
> 又去找 `design` 子目录，`Get-ChildItem` 静默返回空，把耦合当成"零依赖"。
> **扫描结果为空时要先怀疑路径，而不是庆幸。**

## 3. 设计域内部的真实耦合（下一步要处理的）

### 3.1 跨上下文 Mapper 直连

20 个应用服务里有 15 个注入了别的上下文的 Mapper，合计约 30 处。
好消息：**46 个 Mapper 里只有 2 条跨表 JOIN，且都在 library 内部**；
跨上下文的读全是「按 id / `in(ids)` 取一行」，换 Feign 成本很低。

### 3.2 三处跨上下文写在同一事务里 —— 这几对不能拆

| 事务 | 涉及表 | 拆开就会变成分布式事务 |
|---|---|---|
| 建项目（`ProjectAppServiceImpl.create`） | `design_project` + `project_target` + `constraint_set` + `constraint_rule` | 是 |
| 冻结基线（`BaselineAppServiceImpl.freeze`） | `baseline_snapshot` + 回写 `design_project.current_baseline_id` | 是 |
| 激活约束集（`ConstraintAppServiceImpl.activate`） | `constraint_set` + `constraint_rule` | 未跨域 |

**结论：约束（constraint）与基线（baseline）必须留在项目聚合服务里**，
不能像文档章节那样单独成服务。

### 3.3 🔴 `candidate_molecule` 有 5 个写入方 —— 拆分成败的关键

| 写入方 | 写什么 |
|---|---|
| `GenerationPipeline` | insert（生成产出） |
| `ManualCandidateAppServiceImpl` | insert（手工画布） |
| `CandidateVersionAppServiceImpl` | insert（版本派生，挂 parent） |
| `CandidateEditAppServiceImpl` | insert（编辑产物）+ update（`branch_status`） |
| `EvaluationFreezeAppServiceImpl` | update（`total_score` / `hard_passed` / `needs_re_eval`） |

按 R2（数据所有权单一），这张表**只能有一个写入方**。三个选项：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 候选池归 `synpharm-generation`，其他服务通过 `PATCH /internal/candidates/{id}` 改自己的那几列 | 评估/编辑要多一次同步调用；写入方明确 |
| B | 单列一个 `synpharm-candidate` 服务 | 一个聚合单开一个服务，服务数与运维成本都涨 |
| C | 评估侧不反写，改为「读评估快照」而不读候选冗余列 | 排行榜/列表要多一次 join 或缓存，改动面更大 |

推荐 **A**：它保留「生成是候选的第一生产者」这个事实，其余服务只申请变更自己关心的列。
评估回写改成一个幂等 PATCH（`totalScore/hardPassed/needsReEval` 三列），失败可由重试补偿。

### 4.4 跨服务一致性策略

| 场景 | 做法 | 不做什么 |
|---|---|---|
| 设计域读工具注册表 | Feign 同步 + 503 快速失败 | 不缓存到本地表（会出现两个真相） |
| 评估回写候选分数 | 幂等 PATCH + 重试 | 不做分布式事务（R4） |
| 决策读证据包 | 同步聚合 N 个上游查询，结果写 `evidence_bundle` 快照 | 不实时 join 上游表 |
| 生成完成通知评估 | RabbitMQ `afterCommit` 发事件 | 不在事务内发消息（R5） |

### 6.1 过程中的一次真实事故（记录在此，不掩饰）

迁移脚本最初写成「`DELETE` → `INSERT ... SELECT` → `DROP 源表`」，**不幂等**。
我为「查看校验值」把它重跑了一次，第二次的 `DELETE` 把刚搬过去的 12 行删掉，
随后 `INSERT ... SELECT` 因源表已 DROP 而报错 —— `design_tool` 变成 0 行。

**恢复**：重放 `37_design_seed_data.sql`（已改为写 `synpharm_platform`）。
`available` 是探测派生值，platform 启动后 10 分钟内由 `@Scheduled` 重新回写，
实测恢复后 `/api/design/commands` 返回的 `available` 与迁移前一致（`molecule_edit=true` 等）。

**修正**：两个迁移脚本都改成存储过程 + `IF EXISTS` 守卫，重复执行只输出 `SKIP`。
教训是通用的：**搬迁脚本必须能安全重跑**，因为"再跑一次看看"是人最自然的动作。

## 7. 未做 / 明确的风险

| 项 | 说明 |
|---|---|
| Sentinel 熔断限流 | 未引入。当前跨服务调用只有 1 处（Feign），靠 503 快速失败够用；服务数上去后必须补 |
| 链路追踪 | 无 Micrometer Tracing。跨 12 个服务没有 traceId 基本无法排障，建议在第 3 步之前补 |
| Nacos 配置中心 | 各服务仍是本地 `application.yml`，`nacos-config` 依赖在但未真正使用 |
| 事务性 Outbox | 事件发布在 `afterCommit`，但没有 outbox 表兜底「发出去但消费失败」的情况 |
| dev 编排内存压力 | 12 个 Java 容器在本机会吃紧，拆分到第 6 步前需要把 dev 编排改成按需 `--profile` 启动 |
