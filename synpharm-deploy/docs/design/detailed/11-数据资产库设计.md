# 数据资产库（Library）设计说明书

> **文档版本**：v1.0　｜　**日期**：2026-11-03
> **上游文档**：[`08-靶点数据仓库设计说明书`](./08-靶点数据仓库设计说明书.md)（数据治理层）、[`09-数据集清单与清洗标准`](./09-数据集清单与清洗标准.md)（清洗规范）
> **本文定位**：产品功能层。08/09 解决「数据怎么进来、怎么保证可信」；本文解决「数据进来后用户怎么看到、怎么查、怎么拥有自己的库」。

## 0. 与 08/09 的分层关系（先读这段）

这不是第三套设计，而是同一件事的两个视角。**两层不要混用名字**：

```
┌─ 数据工厂（08/09）──────────────────────────────────────┐
│  target_data_source        来源登记（UniProt/PDB/ChEMBL） │
│  target_dataset_release    上游发布版本 + 许可快照        │
│  target_import_batch       导入批次状态机                │
│  target_source_record      来源记录 → 实体映射            │
│  target_alias              别名（检索用，勿另造 synonyms） │
│  target_annotation         字段级证据（raw / normalized） │
│  target_sequence_revision  序列历史 + SHA-256             │
│  target_quality_issue      质量规则命中                   │
└────────────────────┬─────────────────────────────────────┘
                     │ 发布（publish）
┌─ 数据商店（本文）───▼─────────────────────────────────────┐
│  library_dataset       用户看到的「库」（公有 / 私有）      │
│  library_item          跨类型检索投影（标签 + 全文）        │
│  library_item_tag      条目 ↔ 标签                         │
│  library_tag           标签字典（含用户自建）               │
│  library_molecule      分子 / 抗体序列载荷                 │
└──────────────────────────────────────────────────────────┘
```

**术语对照（务必区分）**：

| 概念 | 表 | 谁看得见 | 语义 |
|---|---|---|---|
| 上游发布版本 | `target_dataset_release` | 运维 | UniProt release 2026_03 这次抓取 |
| 库 / 数据集 | `library_dataset` | 用户 | 界面上的一行「公共靶点库」「我的突变体库」 |

一个 `library_dataset`（PUBLIC）由若干次 `target_dataset_release` 发布聚合而成 —— 用户不需要知道上游有几个 release，他只需要看到「公共靶点库 24 条」。

**复用而非重造**：08 已设计 `target_alias`，本文不另造 `target.synonyms`。模糊查询的命中率靠 `target_alias` + `library_item.search_text`（后者是前者的投影）。

## 1. 概念模型

```
库（Library，产品名）
├── 公有数据集   visibility=PUBLIC  owner_id=NULL   全体可读，平台维护
│   ├── 公共靶点库        item_type=TARGET
│   ├── 公共分子库        item_type=MOLECULE
│   └── 公共抗体序列库     item_type=SEQUENCE
└── 私有库       visibility=PRIVATE owner_id=我     可读写，可授权
    ├── 我的 EGFR 突变体库  item_type=TARGET
    └── 我的化合物筛选库     item_type=MOLECULE
```

**一个数据集只装一种 `item_type`**。混装会让字段、导入模板、校验全部退化成 if-else —— 用户要装两类就建两个库，界面上用「库」统一称呼，不逼他理解类型。

靶点只是库中的一种条目，**「靶点库」这个名字废弃**。

## 2. 数据模型

### 2.1 新表

#### `library_dataset` —— 库容器

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `code` | varchar(64) | 唯一；`PUBLIC_TARGET` 等 |
| `name` / `description` | varchar | 展示名 |
| `item_type` | varchar(20) | `TARGET` / `MOLECULE` / `SEQUENCE` |
| `visibility` | varchar(16) | `PUBLIC` / `PRIVATE` |
| `owner_id` | bigint NULL | 公有为 NULL |
| `source` | varchar(20) | `SYSTEM` / `USER_MANUAL` / `USER_IMPORT` |
| `item_count` | int | 由 `library_item` 维护，不做实时 count |
| `status` | varchar(16) | `ACTIVE` / `ARCHIVED`（停用不删） |

#### `library_dataset_grant` —— 授权（笼统版）

| 字段 | 说明 |
|---|---|
| `dataset_id` + `grantee_user_id` | 唯一键 |
| `permission` | 只有 `READ` / `WRITE` 两档 |

**刻意不做**：团队/机构授权（`sys_user.institution` 是自由文本，不能作权限主体）、角色、字段级权限。团队授权需先建 `org` 实体，属独立议题。

**权限语义**：`WRITE` 可增改条目，但**不能删数据集、不能再授权** —— 防权限扩散。

#### `library_tag` —— 标签字典

| 字段 | 说明 |
|---|---|
| `code` PK | |
| `tag_group` | 8 组，见 §4 |
| `tag_type` | `DERIVED` / `CURATED` / `USER` |
| `item_types` | 该标签可打给哪些类型 |
| `owner_id` | 非空 = 用户私有标签，只作用于自己的条目 |

#### `library_item` —— 跨类型检索投影

| 字段 | 说明 |
|---|---|
| `dataset_id`, `item_type`, `entity_id` | 唯一键 `(item_type, entity_id)` |
| `title` / `subtitle` | 统一展示名 / 副标题 |
| `search_text` | 名称+别名+基因名+UniProt+描述 拼接，`LIKE '%kw%'` 用 |
| `quality_level` | `EXPERIMENTAL_STRUCTURE` / `PREDICTED_ONLY` / `NO_STRUCTURE` |
| `derived_from_id` / `derived_from_dataset_id` | 复制血缘 |

**为什么需要这张冗余表**：标签挂在三张专业表上会导致跨类型查询必须 `UNION ALL` 三种形状，标签过滤写三遍，且分页语义会错（每类各取 20 条 ≠ 全局前 20 条）。代价是写入要同事务双写。

#### `library_molecule` —— 分子与抗体序列载荷

| 字段 | 说明 |
|---|---|
| `molecule_kind` | `SMALL_MOLECULE` / `ANTIBODY` / `PEPTIDE` / `OLIGO` |
| `dedup_key` | 小分子=InChIKey，抗体=`sequence_hash`；唯一键 `(dataset_id, dedup_key)` |
| `smiles` / `inchikey` / `canonical_smiles` | 小分子 |
| `sequence_hash` / `heavy_chain` / `light_chain` / `extra_chains` | 抗体 |
| `mw` / `logp` / `tpsa` / `hbd` / `hba` / `rotatable` / `qed` / `pains_hits` | **服务端实算** |

**分子与抗体同表**的依据：现有 `candidate_molecule` 已是这个形状（232 条实数据），字段互补、`modality_code` 区分。拆两张表会让「一个库里同时有小分子和抗体」表达不出来。

### 2.2 现有表改造

| 表 | 改动 | 理由 |
|---|---|---|
| `target` | + `dataset_id` NOT NULL FK | 归属 |
| `target` | + `variant_code` DEFAULT '' | 派生体标识（L858R） |
| `target` | + `derived_from_id` / `derived_from_dataset_id` | 复制血缘 |
| `target` | 唯一键 `uk_uniprot` → `uk_dataset_target(dataset_id, uniprot_id, variant_code)` | 让公共 EGFR 和私有 L858R 共存 |
| `project_target` | + `source_dataset_id` 快照列 | 项目解释「这个靶点当时来自哪个库」 |

**顺手修掉的隐患**：`uk_uniprot` 不含 `deleted`，与已修的 `uk_project_target` 同类 —— 逻辑删掉一个靶点就再也建不回来。私有条目改为**物理删除**（库是物料，无审计义务，真实审计在 `project_target` 快照）；公共条目禁止删除。

**`design_library_item` 不动**：它是知识库字典（MOA/MODALITY/ASSAY），与库是两个东西。其中 `TARGET` 分类无数据，从枚举移除以免与 `target` 表混淆。

## 3. 公共库 mock 数据

规模按「每个筛选维度至少 2 个取值」定，否则标签查询只能返回全部或空。

| 类型 | 条数 | 覆盖 |
|---|---|---|
| 靶点 | 24 | 6 家族 / 9 疾病领域 / 4 成药模态 |
| 小分子 | 19 | MW 129~514，全部为上市药 |
| 抗体 | 10 | HER2 ×2 / PD-1 ×2 / PD-L1 / VEGF / TNF ×2 / CD20 / C5 |

**三个刻意埋的测试点（已落地）**：

1. `KCNH2`（hERG）作为**安全性脱靶靶点** —— 唯一能让「基线块8 风险关注点」与库连通的数据
2. 二甲双胍 **MW=129.167** —— 会被默认硬约束「MW 150~600」真实淘汰，用户能看到约束生效
3. 原有 EGFR / ACE2 / TP53 的 `sequence_length` 是 **24/51/61**，已换成 UniProt 规范序列的
   **1210/805/393**（DTI 与 PPI 的特征按序列长度算，片段会让预测失真）

### 3.1 数据来源与生成链路（`49_library_mock.sql`）

序列、结构编号、SMILES 一律不手写：

| 数据 | 来源 | 说明 |
|---|---|---|
| 靶点序列 / 蛋白名 / PDB 交叉引用 | UniProt REST `/uniprotkb/{acc}.json` | 规范序列与长度 |
| 结构方法 / 分辨率 | RCSB `api/entry/{id}` | 校验 PDB 编号真实存在 |
| 预测模型 | AlphaFold DB `api/prediction/{acc}` | `AF-{acc}-F1`，24 个靶点全部有 |
| 小分子 SMILES | PubChem `compound/name/{inn}/cids` → `property` | CID 与 SMILES 一一对应 |
| 描述符 MW/LogP/TPSA/HBD/HBA/rot/QED/PAINS | **RDKit 2026.03.6 实算** | 与平台评估阶段同一引擎，避免「库里和评估算出来的不一致」 |
| 抗体 VH/VL | RCSB 检索 INN → `rcsb.org/fasta/entry/{pdb}` | 取描述为 heavy/light chain 的链，`sequence_source=PDB_DERIVED` |

**结构覆盖率判定**：UniProt 的 PDB 交叉引用里混着只覆盖几十个残基的条目
（ERBB2 的第一条引用只有 1247-1255 九个残基）。只有 RCSB 记录的实体序列长度
≥ 规范长度 50% 的条目才写进 `target_structure`；达不到的靶点只挂 AlphaFold 全长模型，
完备度如实显示「仅预测结构」。结果分布 **13 有实验结构 / 10 仅预测 / 1 无结构**。

`library_tag.item_types` 同时扩了三处，否则分子与抗体在筛选面板里只能按「阶段」过滤：
`DISEASE_*` → `TARGET,MOLECULE`；`PHASE_*` → `TARGET,MOLECULE,SEQUENCE`；`SOURCE_PDB` → `TARGET,SEQUENCE`。

### 3.2 分子/抗体的质量等级不复用靶点语义

靶点的 `quality_level` 是「结构完备度」，套到分子上会让卡片写着「无实验结构」——
分子本来就没有实验/预测结构这回事。新增两档：

| 等级 | 含义 | 对应标签 |
|---|---|---|
| `MOLECULE_READY` | 结构已确证（SMILES + 描述符齐备） | `QUALITY_STRUCT_KNOWN`（新加，`item_types=MOLECULE`） |
| `SEQUENCE_READY` | 重链与轻链序列完整 | `QUALITY_FULL_SEQ` + `READY_PPI` |

### 3.3 落地记录

- 脚本 `synpharm-deploy/sql/49_library_mock.sql`，**两次执行计数一致**（幂等）：
  24 靶点 / 43 结构行 / 19 分子 / 10 抗体 / 53 检索条目 / 427 标签关联
- 既有 3 靶点只改 `sequence` 与 `sequence_length`，**结构行一概不动** ——
  TP53「无结构」是基线预检 `NO_STRUCTURE` 的演示状态，补一个模型会把 `readiness.tp53` 打穿
- 中文编码坑：`PowerShell | docker exec -i mysql` 会把管道内容按控制台编码转换，
  中文全变 `?`。必须用 `cmd /c "... < file"` 重定向走字节流（第一次就踩了，全表中文被写坏后重灌）
- 前端适配：概览区按数据集类型换维度（靶点＝完备度 / 分子＝分子量分布 / 抗体＝序列长度分布），
  分页时标签写明「本页 N 条」；卡片不再把 `SMALL_MOLECULE` 这类内部枚举直接怼给用户
- 回归：12 个 e2e 套件全通过（347 项断言 0 失败）

**残余说明**：抗体序列取自 Fab 晶体结构，是 VH+VL 可变区而非全长 IgG（约 440 aa）；
`sequence_source=PDB_DERIVED` 与 `note` 字段都写明了来源，不标会让人误以为可直接生产。

## 4. 标签体系

### 4.1 八个标签组

| 组 | 标签示例 | 谁打 |
|---|---|---|
| `SOURCE` | 来自 UniProt / PDB / ChEMBL / 用户导入 | 系统 |
| `FAMILY` | 激酶 / GPCR / 蛋白酶 / 离子通道 / 核受体 / 免疫检查点 / 细胞因子 | 系统（按 InterPro 归并） |
| `DISEASE` | 肿瘤 / 心血管 / 代谢 / 神经 / 感染 / 免疫 / 炎症 / 罕见病 / 眼科 / 呼吸 | 系统 + 人工补充 |
| `MODALITY` | 小分子可及 / 生物药可及 / 两者皆可 / 无成药先例 | 系统 |
| `PHASE` | 已上市 / III / II / I / 临床前 / 未开发 | 系统（ChEMBL maxPhase） |
| `SAFETY` | 心脏安全性(hERG) / 肝毒性关注 / 脱靶风险 / 免疫原性 | 系统 + 人工 |
| `QUALITY` | 有实验结构 / 仅预测结构 / 无结构 / 有全长序列 / 序列为片段 | **系统自动，禁手改** |
| `READY` | 可做 DTI / 可做 PPI / 可做口袋对接 / 可做生成 | **系统自动，禁手改** |
| `CUSTOM` | 我的重点靶点 / 待验证 / 本季度立项候选 | 用户 |

### 4.2 一条必须守住的边界

`QUALITY` / `READY` **必须由系统按实际数据推导，用户不能改**。

原因：基线预检的阻断项（`NO_STRUCTURE` / `NO_SEQUENCE`）就靠这些判断。若用户能把靶点标成「有实验结构」，基线就会放行一个**根本没有结构的靶点**，生成阶段崩在准备环节，且事后极难追查。

| 类型 | 写入方 | 重灌可覆盖 | 用户可改 |
|---|---|---|---|
| `DERIVED` | 清洗/入库计算 | 能 | **不能** |
| `CURATED` | 人工审定 | 不能 | 不能 |
| `USER` | 用户 | **绝对不能** | 能 |

**重灌数据不得冲掉用户标签** —— 清洗脚本最易犯的错：一键重灌清空用户三个月标注。按 `tag_type` 只覆盖 `DERIVED`。

## 5. 查询设计

### 5.1 参数

| 参数 | 说明 |
|---|---|
| `q` | 模糊查询，命中 `search_text`（含 `target_alias` 投影） |
| `tags` + `tagMode` | 多选；**默认 AND**（OR 会让人以为标签没用） |
| `tagGroups` | 限定组内匹配，避免跨组 AND 永远为空 |
| `organism` / `family` / `itemType` | 结构化精确过滤 |
| `mwMin`/`mwMax`、`logpMin`/`logpMax` | 数值区间，仅 `MOLECULE` |
| `qualityLevel` | 直接映射 `library_item.quality_level` |
| `sort` + `page`/`pageSize` | `pageSize` 上限 200 |

### 5.2 标签与属性不能混为一谈

| 查询意图 | 走哪条 |
|---|---|
| 所有激酶 | 标签 `FAMILY=激酶` |
| MW 300~500 的分子 | 数值区间 |
| 激酶里 MW 300~500 的 | 标签 + 区间 |
| 能直接立项的靶点 | `QUALITY=有实验结构` AND `READY=可做口袋对接` |
| hERG 风险靶点 | `SAFETY=心脏安全性(hERG)` |

把「MW 300~500」做成标签会产生几万个动态标签，字典失效。**数值进属性，语义进标签。**

### 5.3 索引

`library_item`: `(dataset_id, item_type)`、`(quality_level)`；`library_item_tag`: `(tag_code, item_id)`、`(item_id)`。`search_text` 先 `LIKE`（<1 万条够用），超限再上全文索引或 ES —— 现在就上 ES 是过度设计。

### 5.4 库作为生成种子源（已实现）

库的第一个**下游消费者**是候选生成：`POST /generations` 的 `seeds[].libraryItemId`。

| 设计点 | 决定 | 理由 |
|---|---|---|
| 谁解析结构 | **服务端**，前端只传 itemId | 前端回传 SMILES 等于把「这条属于你」的校验权交给调用方，别人拿到 id 就能把私有分子塞进自己的批次 |
| 不可见怎么办 | 404，不区分「不存在」与「不是你的」 | 与库的读接口同一条口径 |
| 靶点条目能不能当种子 | 不能，400 `LIBRARY_ENTRY_NOT_SEEDABLE` | 靶点不是候选分子，进 S4 只产出空结构 |
| 小分子用哪个 SMILES | `canonical_smiles`，没有才退回 `smiles` | 同一分子的不同写法在 S5 去重时才会暴露 |
| 名字怎么带到候选 | `generation_params.seedName` → `candidate_molecule.molecule_name` | 版本树从此显示「阿司匹林」而不是 `CCOc1ccc…` |

这条链路的意义不在技术复杂度，而在**可用性**：SMILES 是结构不是名字，
不给「从库里勾选」这条路，没有生物信息背景的用户在第一步就无法开始。

### 5.5 分面筛选（`/api/library/facets`）

库变大之后，「一次列全 + 一个关键词框」会退化成翻页地狱：用户不知道自己要找的在第几页，
也看不出还剩哪些维度可以收窄。生成阶段挑种子就踩在这个问题上，于是加了分面接口。

与 `/tags` 的分工：

| 接口 | 计数口径 | 回答的问题 |
|---|---|---|
| `/tags?datasetId=` | 整个数据集 | 「这个库有什么」——筛选面板要不要显示这个标签 |
| `/facets?datasetId=&tags=…` | **当前筛选结果** | 「下一步还能怎么收窄」——点下去会剩几条 |

**每个标签的计数要扣掉它自己所在组的已选标签。** 选了「肿瘤」之后，「疾病领域」组里
心血管的计数必须是「不看疾病这一维时有多少条」，否则用户点到心血管会发现数量对不上，
或者干脆是 0 —— 那是普通筛选的行为，不是分面。

实现上不按组发 9 条聚合 SQL：每组的约束是「已选标签减去本组」，`HAVING` 的下界随组变化，
一条 `GROUP BY` 表达不出来。改成「一次取全量 (item_id, tag_code) + 内存里逐组扣减」，
在库规模到几万条之前更省也更好读。

**前端同组只能选一个**（换选而非叠加）：这些字典实际都是「一条条目只属于一个家族/一个阶段」，
同组选两个在 AND 语义下必然是空集。界面上标明「每个维度选一个」。

**已选条目独立于筛选结果保存**：筛完再改条件不该把之前勾的丢掉，已选区常驻列表上方，
并提示「其中 N 条不在当前筛选结果里（仍会提交）」。

## 6. 私有库

### 6.1 导入通道

| 格式 | 适用 | 要点 |
|---|---|---|
| UniProt ID 列表 | 靶点 | 批量从公共源补全，用户只填标签 |
| CSV 模板 | 靶点 / 分子 | 表头固定，**逐行报错** |
| SDF | 小分子 | 服务端算 InChIKey / 理化性质 |
| FASTA | 抗体 | 解析重链/轻链 → `sequence_hash` 去重 |

三条纪律：
1. **派生字段一律服务端实算**（InChIKey / MW / `sequence_hash`）—— 前端能填就能造出「看起来对其实是另一个分子」的条目
2. **逐行报错**：1000 行里 3 行有问题，要显示「第 47 行：SMILES 无法解析」，不是「导入失败」
3. **重复策略显式选择**：`SKIP` / `OVERWRITE` / `KEEP_BOTH`（后者需 `variant_code` 区分）

### 6.2 自定义标签

用户可建 `tag_type=USER` 的标签，只作用于自己的条目，不污染公共字典。公共标签可打到私有条目（从 EGFR 复制的条目仍带 `FAMILY=激酶`）。

### 6.3 复制公共条目

`POST /api/library/items:copy` + 目标数据集 id。必须写 `derived_from_id` 血缘；`variant_code` 由用户填（默认空时提示「这是同一条靶点，确定复制」）。

## 10. 已知边界

- **抗体序列入库后评估维度为空**：`fastapi` 理化性质只算小分子（`MetricFieldMapper` 13 个字段全是小分子指标）。序列能存/查/绑项目/当生成种子，但进「评估 → 决策」无指标可算 —— 这是计算层缺口，非库功能可补。
- **抗体序列是 Fab 可变区，不是全长 IgG**：取自 PDB 晶体结构的 heavy/light chain（约 440 aa），标注 `sequence_source=PDB_DERIVED`。可用于 PPI/相似性/展示，**不可直接当生产序列**；全长 IgG 需另接 IMGT/UniProt 抗体库。
- **小分子描述符由 RDKit 计算而非厂商标称值**：与 PubChem 的 `XLogP` 有细微差异（引擎不同），平台内部与评估阶段一致即可；对外发布需注明计算引擎与版本。
- **`target.pdb_ids` 逗号字符串保留**：08 要求「禁止压成单字段」，如实现在 `target_structure` 按 chain 建模，`pdb_ids` 仅作列表页快速展示的冗余投影，不作为权威数据源。
